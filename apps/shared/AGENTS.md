# apps/shared

Shared packages of the one Go module `github.com/tallesborges/zdx/apps` (`apps/go.mod`; Go and toolchain pinned there), which builds the one Go binary `zdx-go` (`apps/cmd/zdx-go`). The gateway (`apps/gateway`), the monitor (`apps/monitor`), the chat TUI (`apps/tui`), and the `quota`, `jobs`, and `git` commands of `zdx-go` import them. The module is not part of the Cargo workspace: the Rust build needs no Go.

## Packages

- `protocol`: engine socket wire types and encodings, no I/O (`crates/zdx-engine/src/orchestration/protocol.rs` and `views.rs` are the source of truth). Status report and capabilities, `ServiceError`, `ErrUnsupported`, view ops with their capability and reply budget, `View`, `DecodeViewReply` (socket reply and `zdx views` stdout), `EncodeLine` (op-tagged request line, no HTML escaping).
- `socket`: the transport. One request line per Unix socket connection; `Call` reads one reply line, `Open` returns a `Stream` of raw reply lines. It never merges, drops, or reorders lines: a client that coalesces streaming deltas does it above this package. Cancelling the context closes the connection. Every transport error wraps exactly one outcome class: `ErrRequestNotSent` (nothing written), or `ErrRequestOutcomeUnknown` (`ErrNoAnswer` when the budget or the caller's context ended; it keeps its text and also wraps the context error). `Status`, `Require`, and `View` ask for status on every call, because the service can restart onto another build.
- `transcript`: the terminal layout of a thread that the monitor and the chat TUI share: the `thread_view` body types, `Merge` (cursor deltas), `Render` (styled lines and tool-row spans; one header per assistant turn, closed by a compact divider of its summed usage, `──  ↑in ↓out · N cached · Nx`; usage, which the engine saves before a request's items, opens a turn too), `Detail` (one call), `Markdown`, and `Clean`/`CleanAll`. Values come from the engine; it derives none.
  - Markdown: message, expanded-thinking, and interruption text, and tool bodies the engine marks `markdown`, are parsed with goldmark v2 (CommonMark + GFM; a source line break is a line break, as in the Mini App's `marked` with `breaks`) and laid out by our own walker: no Markdown punctuation where a format applies, code blocks behind a gutter and hard-wrapped (`┊` continues a line; nothing is cut), tables fitted to the width (narrow: `header: value` lines), raw HTML shown literally and dim, links as `label (url)` with no OSC 8. Tool rows, JSON input, and stream output are never parsed. Every string from the tree passes `Clean` again (goldmark decodes entities, so `&#x1b;` would become ESC; a decoded `&#13;` becomes a space so it cannot hide the text before it). A word wider than the line is split with `fitPrefix`, which measures only what can fit: `ansi.Truncate` on the rest of the word made long tokens quadratic. `Cache` keeps each item's lines per width and theme across rebuilds and drops what a rebuild did not use (`Done`). Glamour v2 was evaluated and not used: it emits OSC 8 links, keeps `##` in headings, and wraps code blocks with broken indent.
  - External text is untrusted: surfaces run `CleanAll` on every answer and `OneLine` on error strings, so escape sequences (SGR, OSC 8, DCS/APC passthrough), C0/C1 controls, and carriage returns never reach Bubble Tea's renderer, which applies SGR and hyperlinks and forwards terminated DCS/APC/SOS/PM sequences.
- `quota`: live subscription quotas of every stored provider account, the one implementation for `zdx quota`, the Mini App, and the monitor. See the package doc in `quota/quota.go`.
- `jobs`: ZDX jobs (docs/SPEC.md §8 Jobs): job files and their flat frontmatter, schedules and cron, the state files (claims, the `flock` run lock, `last.json`, the missed checkpoint, `scheduler.json`, `jobs_runs.jsonl`, the archive), status (`StateOf`, `Summaries`, which the gateway serves to the Mini App), `SetModel`, the run bookkeeping (`Runner`), the scheduler (`PlanTick`, `Scheduler`), and the scheduler's PID file and context record. `Engine` runs the Rust side: `zdx jobs attempt` (one attempt's agent) and `zdx jobs resolve` (settings). See the package doc in `jobs/jobs.go`.
- `gitview`: the Mini App Git views (status, scope, diff) the gateway serves in process, on Rust's `thread_root` view. See `gitview/AGENTS.md`.
- `version`: the zdx version a Go program was built for (`version.Zdx`, set by the linker flag `ldflags.sh` prints from the workspace `Cargo.toml`). `Resolve(explicit)` never guesses: without a flag value or a build value it returns `ErrUnknown`, which says how to build or run with a version.
- `sandbox`: `TestMain` isolation for this module's tests (fresh `HOME`, `ZDX_HOME`, `TMPDIR`; other `ZDX_` variables and `OPENCODE_API_KEY` dropped; a failing `zdx` on PATH; the run fails when the inherited home's OAuth cache or live-service files changed).
- `quota/cli`: `zdx-go quota`, the quota reader `zdx quota [--json]` execs (`crates/zdx-cli/src/cli/commands/quota.rs`, `GoProgram` contract): `--root ROOT --zdx-version VERSION [--json]`. Output is the stdout `zdx quota` printed when it was Rust. It never runs `zdx`.
- `jobs/cli`: `zdx-go jobs`, the jobs program every `zdx jobs` subcommand but `history` execs (`crates/zdx-cli/src/cli/commands/jobs.rs`, `GoProgram` contract): `--root ROOT [--system-prompt TEXT] [--no-thread] [--thread ID] [--zdx PATH] <list|validate|scheduler|runs|set-model|run> ARGS`. Output is what the Rust commands printed. Rust is `--zdx`, else `$ZDX_BIN`, else `zdx` on PATH. The scheduler starts each run as `<this binary> jobs [globals] run …`.
- `gitview/cli`: `zdx-go git`, which `zdx git status|scope|diff` execs (`crates/zdx-cli/src/cli/commands/git.rs`): `--root ROOT [--zdx PATH] <status|scope|diff> [--thread ID] ARGS`, printing the Mini App route body as JSON. Without `--thread` the repository is the one at `--root`; with it, the `thread_root` view comes from `zdx --root ROOT views` (the running service answers, or zdx builds it), with `--root` as the fallback root.

## Rules

- Quota reads credentials read-only: never refresh a token, write `oauth.json`, or take `oauth.lock`. Rust is the only writer.
- Runtime environment: credentials come from `$ZDX_HOME/oauth.json`, and OpenCode Go from `OPENCODE_API_KEY` in the environment of the process that reads quotas (the bot service for the Mini App, the shell for `zdx quota` and the monitor). launchd services get no `OPENCODE_API_KEY` unless it is set for launchd.
- Never log or print a token, a credential field, or a provider response body. Errors name files and fields, not values.
- A failure to read the account store is an error (`quota.ErrDiscovery`), never an empty healthy list. A missing `oauth.json` is no accounts.
- Jobs state is live data the user's scheduler depends on: keep every file format docs/SPEC.md §8 Jobs defines, read existing state as is, and never rebuild or migrate it. A format change goes into SPEC first and must be read by both `jobs` and the Rust readers (`zdx_engine::jobs::records`, `zdx_engine::job_scheduler`).
- Tests use synthetic homes, `httptest` servers, fake credentials, and an explicit synthetic `Version`. No real home, credential, provider endpoint, or live service. Create Unix sockets under `os.MkdirTemp("", ...)`: macOS limits socket paths to 104 bytes.

## Build and checks

- `just shared-check`: `gofmt`, `go vet`, and `go test -race` for `./shared/...` and `./cmd/...` from `apps`; `just go-check` runs them for the whole module. GHA vets and builds the whole module and runs these tests on Linux (`go` job, Go from `apps/go.mod`'s toolchain line), so keep tests portable.
- `just jobs [ARGS]`, `just quota [ARGS]`, `just git [ARGS]`: build `apps/bin/zdx-go` without the Mini App (`apps/build.sh --no-web`), then run the `zdx` command from this checkout with `ZDX_GO` pointing at it.
- Deploy `zdx-go` with `zdx` (`just deploy` / `just safe-deploy`, never `just install` alone): the Rust commands jobs run (`jobs attempt`, `jobs resolve`) and `zdx jobs` delegating to it ship together, and Rust has no quota view, so a new `zdx` with an older Go binary leaves quotas `pending`/stale (gateway) or failing (monitor). The scheduler service runs `zdx jobs scheduler`, so its next restart after a deploy runs the new scheduler.
- Every build passes `-ldflags "$(apps/shared/ldflags.sh)"` (`apps/build.sh` does). With `go run` from `apps`, add `-ldflags "$(shared/ldflags.sh)"` or pass `--zdx-version`.
- Opt-in Rust checks against a built binary: `ZDX_GO_TEST_BIN=<abs path to zdx-go> cargo test -p zdx --test integration -- jobs_go quota git_go`.
