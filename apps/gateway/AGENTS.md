# apps/gateway

The zdx Telegram bot and Mini App server, in Go. It replaced the Rust bot (`crates/zdx-bot`, removed; comments and test names that cite its files refer to git history). Independent Go module (`go.mod`; toolchain pinned there), not part of the Cargo workspace: the Rust build needs neither Go nor `apps/web`, and this module builds without cargo. `gateway.Missing` (`internal/gateway/run.go`) is empty; `gateway.AcceptanceChecks` lists what only a deployment can check. `zdx-gateway serve` only points to `--root ROOT bot`.

## Running it

- Service: `zdx service install bot` runs `~/.local/bin/zdx-gateway --root ROOT bot` under launchd (the default bot program; `--program` overrides it, and its read-only `preflight` must report ready first). Install or refresh the binary with `just gateway-install`; `just deploy` and `just safe-deploy` refresh it with `zdx` before the restart.
- Foreground: `zdx bot [-- ARGS]` replaces itself with the gateway (`$ZDX_GATEWAY`, an absolute path, else `~/.local/bin/zdx-gateway`) with the same argv, this `ZDX_HOME`, and `ZDX_BIN` set to that `zdx` unless already set. It fails before running anything when the gateway is missing. `just bot` builds both from this checkout and runs them that way. `bot.pid` refuses a second bot on one `ZDX_HOME`: stop the bot service first; never run a local bot with the production token while the service runs on another home.

## Boundaries

- Go owns Telegram transport, intake, presentation, and HTTP. Rust owns providers, tools, execution queues, steering, cancellation, workers, thread/index writes, and config resolution. Do not port engine rules into Go; ask for a socket operation with a CLI twin instead.
- Go talks to Rust only through the orchestrator socket (`$ZDX_HOME/run/orchestrator.sock`, NDJSON, one request per connection). `crates/zdx-engine/src/orchestration/protocol.rs` is the source of truth; `internal/engine/protocol.go` mirrors it.
- Check the exact capability (`StatusReport.Has`, `Client.Require`, `RequireAll`) before any new operation or field. A routed turn is not submitted, and the renderer subscription is not opened, without `gateway.TurnCapabilities` (reply parts, delivery records, hold tokens): no reply may go out unrecorded.
- Holds (Rust holds v7.2, capability `hold_tokens`; contract in the Rust lead's `rust-holds-v7.md`): a token comes only from a direct reply, never an event: a followed turn's from its `submitted` reply (`Submission.Holder`), every unfollowed turn and every `turn_replay` from the renderer's `subscribed` reply. The bridge asks for the capability on each connection and reads that reply whenever the service has `hold_tokens`, with or without the replay opt-in; `replay` is sent only with the capability. Releases and records of a held turn carry turn id and that token; never send `force`. The first Telegram send of a held turn waits for the pending record's acknowledgement (one retry with the same id after no answer, none after a refusal); without it nothing is sent, the reply is lost and logged, and the hold is released. Renderer and followers opt in to replay (`replay:true`); a replay posts only the reply (or a failed turn's error), no status message, and no touched-worker links (`turn_replay` carries none; the Rust bot has no replay at all, so this loses nothing it had). A refused renderer subscription (`conflict`) is retried 3 times over about 2 s, then `Run` fails with `bot.ErrRendererConflict` (non-zero exit, never 42). `Client.Release` without a token remains only for services before the capability.
- Go writes no thread, SQLite, OAuth, or run state, except what it owns for the bot (agreed with Rust): attachments under `$ZDX_HOME/telegram/<chat>/<message>_<name>`, topic blocks under `$ZDX_HOME/telegram/unsetup-topics/<thread>`, and `$ZDX_HOME/run/bot.pid` and `bot.supervised` (decimal PID, as `zdx_engine::pidfile` writes them).
- Never run two gateways for the same token: two pollers split updates, and two `subscribe{renderer:true}` connections fight over routed-turn holds. `bot.pid` (flock plus a live-PID check) refuses a second bot on one machine; a 409 from `getUpdates` stops polling.
- Telegram updates have no delivery guarantee: neither at least once nor at most once, as in the Rust bot. Telegram confirms a batch only with the next poll, which the gateway sends right after it hands the batch to in-memory intake queues, before the work reaches Rust. Loss: a crash after that poll loses every update of the batch not yet submitted (still queued, downloading, or composing). Duplicates: a crash before that poll redelivers the whole batch, and updates already submitted run again (no update-id dedupe). A clean stop confirms with one last poll only after a complete drain; a drain that times out confirms nothing, so the batch comes again (duplicates possible). Updates in that last poll's own answer are not handled and stay for the next process. Never resend an unknown send.
- The orchestrator service must answer before a batch is handed off (`Poller.Ready`, one status call): while it does not, the poller waits and does not poll again, so the batch stays unconfirmed (a stop or crash then gets it again). This narrows the outage window; it adds no guarantee: after hand-off the next poll confirms the batch, and the loss and duplicate windows above hold unchanged. When the service goes down after the check, intake sends a request again only when it was never sent (`engine.ErrRequestNotSent` without `ErrRequestOutcomeUnknown`; a failed capability check before a submit counts as not sent), for up to `NotSentRetryWindow` (30 s) on the topic queue, then tells the user; a crash in that time loses the update. An ambiguous submit is never sent twice. Other service calls (General topic setup, commands, image preparation) fail at once with a notice; a failed transcription leaves the audio path with "transcription unavailable" for the agent, as a provider failure does.
- Settings: profile bindings follow config edits as the Rust bot's per-turn reload does (`SettingsWatch`): before each update is handed off and each Mini App write, Go stats `config_layers` from `zdx telegram settings` and loads the settings again only when one changed; every copy of `Settings` reads the current profiles (`RootForChat`, chat bindings, feedback root). Token, allowlists, server and root stay as started, as in Rust. Without `config_layers` (older zdx) nothing reloads.
- `bot.Admission` gates new outside work: each polled update (until it is handed off) and each Mini App write. A queued-restart check closes it (waiting for admitted work), checks `Deps.Idle`, asks Rust (`run-queued-restart`, cut after `QueuedRestartTimeout`), and opens it again unless the gateway exits; a check that timed out has an unknown outcome (services may have restarted), so the same request file is not checked again until it changes; exit shuts it, so held updates are neither handed off nor confirmed and waiting writes get 503. Read `Deps.Idle` only with admission closed.
- Delivery records: every send of a held turn waits for its acknowledged pending record, including a follow-ups-only reply (an empty record) and a failed replay's error (a recorded text). The outcome record gets one retry with the same id; if it still fails, the reply stays sent and the record stays pending (logged). A release with no answer is retried with the same token (`ReleaseAttempts`); a refusal is final.
- `/model set|reset`: in General it writes the chat default (`set_chat_model`; reset shows it); everywhere else (topics, private chats, groups without topics) it sets the conversation thread's model through `update_thread` with the chat root as `config_root`. Rust checks a mode against the modes of the thread's stored root (`use_modes_of`).
- Tests run in a sandbox (`internal/sandbox`, `TestMain` in `cmd/zdx-gateway`, `internal/bot`, `internal/gateway`): fresh `HOME`, `ZDX_HOME`, `TMPDIR`, every other inherited `ZDX_` variable dropped (`ZDX_GATEWAY_RUST_ZDX` stays), a failing `zdx` on PATH in `cmd`, and while `ZDX_GATEWAY_TEST_SANDBOX` is set the pidfile, supervision marker, settings, lifecycle commands, worktrees, attachments and topic blocks refuse any home outside it. The run fails when a file in the inherited home's `run/` changed. Never bypass it; new packages that start the gateway or run zdx add the same `TestMain`.
- `gateway.Missing` lists implementation gaps and blocks `serve`; `gateway.AcceptanceChecks` lists checks that need a deployment (real Bot API, launchd) and does not block it. `TestMissingNamesEveryUnwiredDependency` walks the production wiring (`serveComponents`): every nil handle of `Components`, `bot.Handler`, `Presenter` and `Deliverer` must be named in Missing as `(<Type>.<Field>)`, every nil `commands.Handler` interface as `(<Field>)`, as must `prepare_photo` while replies use `CheckOnlyPhotos` and `touched_workers` while `engine.Event` lacks it; a wired one must be dropped.
- Never run `zdx service` restart commands against the real `ZDX_HOME` or launchd in tests: use a fake runner or a temp home where they only read pidfiles.

## Layout

- `cmd/zdx-gateway`: entrypoint (`check`, `serve`, and `--root ROOT bot [--zdx PATH] [--web-dist DIR]`, the argv the bot service gives launchd and `zdx bot` execs). `bot` runs `gateway.Serve` (it refuses while `gateway.Missing` is not empty) and exits with code 42 when a restart asks for it. Its tests set a temp `ZDX_HOME`: `bot` starts the gateway in the home it finds.
- `preflight --root ROOT --json`: read-only readiness check `zdx service install bot` runs before it replaces the bot service (`gateway.Preflight`): `Missing`, the engine binary (printed as `zdx`; must be an executable file), settings, Mini App build, every capability the gateway uses (`gateway.ServiceCapabilities`), and the service's `views_root` (must be the same directory as `--root`). No pidfile, no Telegram, no service command; an unreachable orchestrator service is a warning.
- Engine binary: `--zdx`, else `$ZDX_BIN` (the bot plist sets it), else `zdx` on PATH (preflight warns: launchd may resolve another one).
- `build.sh` (`just gateway-build [OUT]`): release build without cargo: runs the Mini App build, copies `apps/web/dist` into `internal/gateway/webdist/dist` (gitignored) and builds with `-tags webdist`. Without the tag nothing is embedded and the Mini App needs `--web-dist`; a missing `index.html` refuses the start.
- `internal/engine`: socket client, protocol types, followed turns (`SubmitFollow`, `PumpTurn`).
- `internal/telegram`: Bot API client: failure classes (ambiguous sends are never resent), per-chat pacing, `Immediate`/`Paced`/`Reliable` modes, token-free errors and logs. `rich.go` flattens rich messages exactly as the Rust bot's `telegram/rich.rs` did; intake reads `Message.PlainText()`, never `Text` alone.
- `internal/bot`: allowlist gates, poller (memory-only offset), album grouping, intake (`handler.go`), turn presentation (`present.go`: status, Cancel, progress), reply delivery and records (`deliver.go`), steer acknowledgements, renderer bridge and hold release.
  - `engine.Buffer` may coalesce only streaming deltas; every other event, unknown types included, is kept in order.
  - Per-topic intake queues order Telegram intake only, up to the submit. The Rust service owns the execution queue, steering, and cancellation; a running turn must never block its topic's next message.
  - Intake order follows the Rust bot: resolve, worker mirror (everything verbatim), commands, staged input, blocked topic (`blocks.go`), turn capabilities, media capabilities, attachments (`internal/intake`), compose, submit. Photos and image files need `prepare_image`, voice and audio `transcribe_audio`; without the capability the message is refused before any download, so intake never drops an image or a transcript silently. A failed download offers "Try again", which dispatches the same `Incoming` again.
  - Queue bypass (`QueueBypass` in `hooks.go`): commands the commands package answers while a topic is busy, and the question of a live `/btw` session, run off the topic queue. A `/btw` question is matched by the thread the topic last resolved to and only when it is newer than the `/btw` command; synthetic messages never match. A bypassed question whose session ended gets the stale notice and never runs a turn.
  - `/queue <text>` (read as typed, after the queue bypass) runs <text> with delivery `queue`. Slash text, bot-made (synthetic) messages and staged-command input also queue; everything else steers (Rust `route_steer`, `steer_eligible`). `cancel_q:` buttons come only from the Rust bot and answer "Already processing": queued input is cancelled with the turn's Cancel button through the service.
  - `general.go`: a General message that is no command opens its own topic (Rust `bot/queue.rs`): name from its first line, orchestrator-marked in orchestrator chats (fail closed), header, the original forwarded, then intake in the topic with the answer quoting the General message (`Origin.Quote`, `reply_parameters`), and a launcher repost. A topic opened from General or with `pending_topic_title` is titled from its first message by Rust `generate` (title); the thread stores the title only after the rename succeeds. A new Threaded Mode thread in the bot's private chat becomes an orchestrator, as in Rust. Setting a profile or a model on a new thread sends the chat root as `config_root` (Rust checks it there) and stores no root: the first turn records the root it runs in, as in the Rust bot. A General topic whose orchestrator setup fails is blocked (`TopicBlocks`), so no later message runs the default agent there. A new Threaded Mode orchestrator gets `pending_topic_title`. The commands package supplies the hooks (`TopicHooks`).
  - `mirrors.go`: the legacy mirror-topic feed (Rust `orchestrator.rs`): orchestrator prompts, one live status line per worker turn (edited at most every 3 s, with `⏹ Cancel worker` and `💬 Open Thread`, deleted at the end), and the result. The mirror topic comes only from `WorkerSnapshot.mirror{chat,topic,thread_id}` (capability `worker_mirror_route`), never from a `t.me` link. A found mirror is kept until the renderer subscription opens again (`MirrorFeed.Forget` through `Bridge.Connected`: the service may have restarted); none is asked again after a minute; a route whose `thread_id` is not `telegram-<chat>-topic-<topic>` is ignored.
  - `workers.go`: worker events from the renderer subscription. They run off the bridge loop, in order per owner thread (`WorkerNotices.Dispatch`), so a slow Telegram call delays only that owner. A finished worker turn posts the Rust one-line notice in its orchestrator's topic before the review turn: the bridge waits for the owner's backlog before it renders a service-started turn (`Bridge.Before`). Title from the `thread_workers` view; worker changes refresh the owner's pinned header through the commands hook. The legacy mirror feed still holds `MirrorFeed.mu` across Telegram calls (all mirrors, not the bridge).
  - `present.go`: a Cancel request is not a cancellation: the status says Cancelled only when the turn ended interrupted (or never ran); a turn that completed or failed first shows that outcome. A replayable turn (replay opt-in with a hold token) whose connection is lost shows `StatusConnectionLost`, with no error and no Try again: its reply comes as a replay if the turn finishes.
  - `CommandRequest.HasLoadedImagesOrAudio` comes from the intake result across the album; with it, no command runs (Rust), staged input still does. `Incoming.Synthetic` marks text the bot builds (command picker taps, launcher seeds, Mini App feedback): it never starts or answers a staged command or matches the `/btw` bypass. Follow-up taps stay non-synthetic, as in Rust. This differs from Rust on purpose for a picker tap during a staged command (see `hooks.go`).
  - `hooks.go`: `CommandHook`, `StagingHook`, `CallbackHook` for `internal/commands`. `bot` never imports `commands`; the built-ins `/new` and topic `/model set|reset` (`commands.go`) run before the hook. A hook returning false sends the message on as text.
  - `ServiceArtifacts` (`filecard.go`) finds Send file targets through the `artifacts_list` and `artifact_resolve` views.
- `internal/conversation`: thread id <-> chat/topic.
- `internal/engine/views.go`: read-only views (`views.rs`), each gated by its capability; bodies pass through unchanged.
- `internal/gateway`: startup (`serve.go`: pidfile first, settings, assets, supervision marker), lifecycle (`lifecycle.go`: `/restart` and the queued-restart poller over `zdx service restart-peers|restart --queue --thread|run-queued-restart --json`; the gateway restarts itself only by exiting 42), shutdown as a drain (`Run`: stop polling, confirm handed-off updates, finish started work, cancel after `DrainTimeout`), wiring (`BotComponents`, `Run`), settings (`zdx telegram settings --include-token`, piped or run by `LoadSettings`), `miniapp.Engine` adapter over the views (`miniapp_engine.go`), attachments with Rust image preparation and transcription (`media.go`), commands wiring (`commands.go`; `helpers.go`: the commands package's Generator, Seeds, Models, ChatDefaults, Launches, Statuses and CommandSource over Rust `generate`, `btw_seed`, `topic_start`, `catalog`, `set_chat_model` and `update_thread`, each request with the chat root; picker scopes `newthread`/`neworch` go out as `new_thread`/`new_orchestrator`), process files and CLI adapters (`process.go`: `LoadSettings`, `CLIWorktrees` over `zdx worktree ensure`).
- `internal/render`: Markdown to Telegram HTML, splitting, reply planning (`PlanReply`) and plan execution (`Deliver`); `internal/bot` supplies the sender, records and photos (`ServicePhotos`: Rust `prepare_photo`; `changed:false` uploads the file as read, `changed:true` Rust's bytes; a photo Rust cannot prepare fails its item, with no document fallback, as in the Rust bot). Touched-worker links come from `turn_ended.touched_workers` (`ServicePlanner`: mirror link from the worker's `mirror_url`, else the Mini App; title from `thread_workers`).
- `internal/miniapp`: Mini App HTTP layer; see its own `AGENTS.md`.
- `internal/intake`: attachment collection for incoming messages (separate owner). Saves files as the Rust bot does (see Boundaries).
- `internal/commands`: slash commands, staged commands and pickers behind the `bot` hooks (separate owner).

## Module

- `go.mod` pins the toolchain and dependencies. Check a new dependency's latest release and module path (`/v2` and later) on GitHub or the module proxy before adding it.
- goldmark is pinned at v2 on request; its README calls v2 an early release, so check Markdown output after any bump.
- Do not run `go mod tidy` while a required module is imported only behind a build tag; tidy drops it.

## Checks

From `apps/gateway`: `gofmt -l .`, `go vet ./...`, `go test -race ./...`.

Opt-in plain-text check against the real Rust service, with a prebuilt binary. The test never builds Rust and fails on a binary that lacks the needed capabilities. Tests that check a newer Rust feature (hold tokens, `feedback_submit`, `prepare_photo`, `config_layers`) skip on a binary without it; with `ZDX_GATEWAY_RUST_STRICT=1` every such skip, and a missing `ZDX_GATEWAY_RUST_ZDX`, fails instead (`sandbox.RustBinary`, `sandbox.RustFeatureMissing`). Gate runs against the binary that should have everything set it. The Mini App package's own real check (`internal/miniapp`) still skips without a binary. The child gets only `PATH`, `TMPDIR`, `LANG`, `LC_*` from the parent, then a temp `HOME`/`ZDX_HOME`, a mock provider, and a fake Bot API (`childEnv`, tested by `TestChildEnvKeepsOnlyTheAllowlistAndTestSettings`): `ZDX_GATEWAY_RUST_ZDX=$PWD/../../target/debug/zdx go test -timeout 400s -run 'RealRust|RealZdx|RealRouteParity|RealFeedback|RealGateway|LifecycleWithRealZdx|RealSettings' ./internal/bot ./internal/gateway ./internal/miniapp` (the Mini App check compares every read route with the Rust view provider, not Rust's HTTP server; see `internal/miniapp/AGENTS.md`). Scenarios: plain text, reply with files (upload, missing file, photo needing preparation, Rust's summary), retry (rerun), cancel, steer that runs as the next turn through the renderer subscription, profile topic, document album through intake, photo and voice through `prepare_image` and `transcribe_audio`, voice with transcription configured in the chat root against a mock endpoint (transcript, and a provider failure that keeps the saved path), Send file and `thread_view` through the views, a real worker created by an orchestrator turn whose `worker_update` turn the renderer bridge delivers, a legacy mirror topic (thread fixture) queueing to that worker, and two overlapping turns whose Bash calls each see their own `ZDX_THREAD_ID`/`ZDX_ARTIFACT_DIR` (`rust_test.go`, `rust_scenarios_test.go`, `rust_workers_test.go`). With a binary that has `hold_tokens` the bot side runs as in production (tokens, replay opt-in), and `rust_holds_test.go` checks holds v7.2: replay after follower loss and after renderer loss, a crash after the pending record ending `unknown` with no second replay, renderer conflict, and refused records and releases. Those skip on a binary without the capability. With the v8 capabilities: photos through `prepare_photo` (unchanged, resized, undecodable), touched-worker links, the legacy mirror feed after a service restart (`realRust.restartService`), and Mini App feedback queued as an unfollowed turn the bridge renders (`rust_feedback_test.go`). `TestRealGatewayEndToEnd` (`internal/gateway/rust_e2e_test.go`) runs the whole gateway as `serve` wires it: a polled message and its reply, then Mini App feedback over HTTP with its chat notice, the bridge-rendered answer, and a duplicate, then a message polled while the service is stopped (held unconfirmed, no notice) answered once after it starts again. `TestRealGatewayCommandFlows` (`rust_flows_test.go`) runs the helper and catalog flows the same way: preflight ready against the service, a General message opening a titled topic, `/status`, `/tldr`, `/commands` with a project command, `/model` in a topic and in General (the chat default written to the temp root's config), `/btw`, `/handoff`, the prompt builder, `/new` with a pending title, a launcher mode, a private Threaded Mode thread, and an orchestrator chat (General topic and launcher). Its fake clock skips Telegram pacing sleeps (a group allows 20 new messages a minute).

Other tests use synthetic fakes only: `httptest` Bot API, a fake socket service, fake clocks. No real token, `ZDX_HOME`, network, or live service. Create Unix sockets under `os.MkdirTemp("", ...)`, not `t.TempDir()`: macOS limits socket paths to 104 bytes. A real service is ready when a status call succeeds (`waitListening`), not when its socket file exists: Rust creates the file before its listener accepts, and a connect in between is refused (about 1 in 20 starts under parallel load). Likewise Rust drops a closed renderer subscription a moment after the client closes it: a test that subscribes as renderer right after stopping another retries `conflict` for a few seconds (`rawRenderer`), as the bridge does.
