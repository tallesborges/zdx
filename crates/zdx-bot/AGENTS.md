# zdx-bot development guide

Scope: Telegram bot runtime, ingest/handler flow, queueing, and Telegram API integration.

## Where things are

- `src/lib.rs`: bot crate entrypoint
- `src/delivery_tracker.rs`: process-local set of reply deliveries in flight (`ActiveDeliveries`, RAII `DeliveryGuard`), owned by `BotContext` and passed to the Mini App server; `send_final_response` starts it before writing the pending record and drops it after the outcome is persisted, and `/api/threads/{id}` reports it as `delivering`, sampled around the event read with `observe` so the flag and the returned events cannot disagree. The key is the effective thread id: `get_thread` resolves an alias (`resolve_alias_id`) before reading events and the tracker, and keeps the requested id and its topic link in the response.
- `src/file_card.rs`: HTML file cards and the `⬇ Send file` button (`sf:<key>`). `response.rs` posts a card instead of uploading an HTML file that has an `Open artifact` link (`is_card_file`); the tap handler answers first, resolves the key from the card's chat/topic through the thread's artifact list and `resolve_artifact_for_download`, uploads the current bytes as a reply to the card on its own task, and records only a successful upload. Never edits, deletes, or refreshes cards. A refused `answerCallbackQuery` (`query is too old`) marks a stale tap: nothing is uploaded and one notice per card per `STALE_NOTICE_WINDOW` asks to tap again. In-flight and stale-notice state is per process (`SendFileState` on `BotContext`).
- `src/followups.rs`: end-of-turn follow-up suggestion buttons (`<followups>` tag → tap dispatches new turn). The keyboard rides on the reply message itself (`keyboard` + `register`); only a text-less reply gets the separate `send_followups` message. Taps and Dismiss edit only the keyboard (`editMessageReplyMarkup`), never the text, because the message is usually the answer, and keep the message's link rows (`Message::link_rows`, read from the callback's `reply_markup`, so a captioned file's `Open artifact` survives even after a restart).
- `src/retry.rs`: post-failure "Try again" buttons (`RetryAction`, `retry:go`/`retry:x` callbacks). `Turn`: a turn that failed without a reply re-runs from persisted thread state (no new user message). `Download`: a message whose attachment download failed after every try is held whole and, on tap, dispatched again through the topic queue (`offer_download_retry`, posted by `handle_message` on `ingest::DownloadUnavailable`)
- `src/server.rs`: embedded HTTP web server for the unified Mini App. Serves the built Svelte app from `apps/web/dist` via `rust-embed` — `/app` is the SPA entry point (`no-cache`), `/app/{*path}` serves content-hashed assets (`immutable`, one year), and `/threads` / `/monitor` are compatibility aliases for the same shell. Responses are gzip-compressed via `tower_http::CompressionLayer`. Every `/api/*` endpoint requires fresh bot-token-signed Telegram `initData` from an allowlisted user, and every `/api/*` request is timed by the `log_api_timing` layer (method, path, status, elapsed) — `debug` normally, `info` past `SLOW_REQUEST`, since the SPA shell renders from embedded assets and any visible "loading" is one of these requests still in flight. The read-only monitor snapshot is built off the async hot path and cached for 30 seconds, except `active_agents`, which `get_monitor` reads from the run markers on every request (a few small files) so a cached snapshot never delays live status; concurrent requests on an expired cache wait for one single-flight build (`monitor_build`), since the Mini App opens several monitor views at once and each build may sync the usage cache. A request cancelled mid-build releases the guard while its blocking build keeps running, so the next request may start a second build. **Live quotas are never awaited on the request path**: `/api/monitor` overlays the last known snapshot and kicks off a background refresh (single-flight via an owned mutex guard, so a panic cannot wedge it), because a quota fetch hits every stored OAuth account with a 10s per-request timeout and no shared deadline. The overlay is applied per request rather than cached with the snapshot, so a refresh landing mid-window is served immediately. `subscriptions_status` (`ready`/`pending`/`stale`) is what keeps an empty list before the first fetch from reading as "no subscriptions"; the quota values themselves come from the same shared snapshot API as `zdx quota`. Git inspection resolves the selected thread root before the bot root and bounds lazy per-file diffs. Diffs are scope-aware: `/api/git` returns the uncommitted status, and `/api/git/scope?scope=all|<hash>` lists the files a history scope touches (`all` = merge base with the repository's **main branch** against the working tree, so it shows what this branch adds the way a pull request would, plus local edits; on main itself that equals uncommitted. The main branch is read from `origin/HEAD`, falling back to `main` then `master`, preferring a local branch over its remote; with none found the base is `HEAD`). Revisions reaching a `git` argument list are validated as 7–40 hex characters by `valid_commit_hash`, so nothing readable as an option or a range is ever passed. `/api/threads` lists the 50 most recent top-level threads (`?kind=workers`: only workers, via `thread_persistence::list_recent_workers`), limited in SQL, each carrying an `is_worker` flag (`ThreadSummary::is_worker`) and a `t.me/c/<internal_id>/<topic_id>` link when the thread id encodes a supergroup topic. `/api/threads/{id}/workers` lists an orchestrator's workers by merging two sources that are **not** equivalent: live `WorkerSnapshot`s from the in-memory `WorkerManager` (held on `ServerState`), and children recovered from `thread_meta.parent_thread_id`. The persisted half restores *discovery* only — a recovered row is returned with `live: false` and `status: "unknown"` rather than being reported as settled, because runtime state does not survive a restart. Persisted children are filtered by `ThreadSummary::is_worker`: the same parent link is used by subagent and helper runs, which are not workers. The same merge feeds `ThreadResponse.worker_count`, which gates the Mini App's Workers tab, alongside `parent_thread_id`/`parent_title` for the breadcrumb out of a worker thread. Both the workers route and the lineage lookup resolve one `alias_to` hop first (`resolve_alias_id`, same rule the Git route uses): Mini App deep links carry the *topic session* id, and a worker mirror topic is an alias whose own thread file has neither lineage nor workers, so skipping the hop makes a worker opened from its mirror look parentless. `/api/threads` additionally returns a per-row `workers` roll-up for orchestrators, built from `thread_index::worker_counts_for_parents` — one indexed `GROUP BY` over just the ids on the page being rendered, not a corpus scan — unioned with live statuses from `WorkerManager::statuses_by_owner`. `failed` is its own bucket in that roll-up rather than part of `settled`, and `total` takes the larger of the live and persisted counts because the index syncs on a freshness window and can lag a just-created worker.
- Mini App workspaces API: `GET /api/workspaces` is a read-only, uncached adapter over `zdx_engine::workspace_config::report(Some(bot root))` — every workspace with its model settings, origin layers, and inherited fallbacks. No write route exists.
- Mini App trajectory API: `GET /api/threads/{id}/trajectory` is a thin adapter over `zdx_engine::core::thread_trajectory`; it adds bounded live-tool marker snapshots but owns no timing, ranking, overlap, or legacy-data semantics.
- Mini App artifact feedback: `POST /api/threads/{id}/artifacts/feedback` is the Mini App's one write route. `server.rs` takes the user id `authorize_api` put in the request extensions (`AuthorizedUser`), refuses `active`, resolves the destination from the *requested* id (`artifact_feedback::resolve_destination`: Telegram chats and topics only; worker threads opened directly and TUI/CLI threads are a `409`, never rerouted — direct worker delivery was tried and dropped because `enqueue_from_topic` re-attaches an unmanaged worker as self-owned after a restart and its result reaches no chat), checks the sender may write there (`route_allowed`, the queue's own gate, checked first because the queue drops a refused message silently), holds a per-submission in-flight key, then calls `zdx_engine::core::artifact_feedback::save_feedback` on the alias-resolved id with a `user=…;dest=…` binding (retry identity). Delivery runs on its own task so a client disconnect cannot cancel it mid-queue. `BotFeedbackSink` builds the synthetic `SyntheticKind::ArtifactFeedback` message with labelled `Message::local_attachments`, writes the bundle's `queued` marker (a failure queues nothing), posts a `📝 Feedback on …` notice, and dispatches through the per-topic queue; a legacy mirror topic then forwards it to its worker via `route_worker_topic_message` like a typed message. Status codes: `412` changed file (client offers send anyway), `409` id reused with other content, in-flight, or unsupported thread. `limit_feedback` takes an owned permit (`FEEDBACK_CONCURRENCY`) before the body is read and hands it to the handler (`FeedbackPermit`), which moves it into the blocking save, so a client that disconnects mid-decode does not free the slot while the decode and render still run. `GET /api/threads/{id}/artifacts/image` is a thin adapter over `artifact_feedback::canonical::canonical_for_artifact` (the canonical copy the Mini App previews and annotates): identity in `X-Zdx-Source-Sha256` / `X-Zdx-Canonical-Sha256` / `-Width` / `-Height`, `422` with the engine's reason when the image cannot be annotated, at most `IMAGE_READS` previews reading originals at once (requests wait; the permit lives in the blocking task). Making copies is bounded by the engine's process-wide `canonical::MAX_NORMALIZATIONS` gate, shared with feedback saves; `FeedbackError::Busy` (no slot within 60 s) maps to `503` on both routes. The gate is taken innermost, after every request permit, so it cannot deadlock with them. It bounds how many decodes run; their size is bounded by the engine's source limits (25 MiB, 40 MP; up to about 480 MB of heap per decode for the costliest encodings measured, see SPEC). Images attached to a note are decoded later by ingest (`load_local_image`), outside the gate. For feedback the engine returns the marked copy and close-ups as labelled images in `SavedFeedback.images`, and `feedback_attachments` passes them on in that order; the marked copy fits the inline limits, so ingest sends its bytes unchanged. Route tests use a recording `FeedbackSink`; `BotFeedbackSink` is tested against the fake Bot API with a captured dispatch through ingest (for an image artifact, down to the image blocks `record_user_message` builds), never a real chat or model turn.
- Mini App artifacts API: `GET /api/threads/{id}/artifacts` lists the shared `zdx_engine::core::artifacts` projection (artifact-dir files merged with transcript `<media>` refs, deduped), `GET /api/threads/{id}/artifacts/file?path=…` serves one file inline. `GET /api/threads/{id}/artifacts/version?path=…` answers the file's SHA-256, size, and modified time with the same resolution (`ServerState::artifact_versions` caches hashes per path while length and mtime stay the same; `artifacts::file_sha256` streams the read). Transcript messages carry the same rows as `artifacts` so the thread renders them inline; the tab is just the merged view with preview/open, download, and Go to message. Each row carries the projection's opaque `key`, which `Open artifact` deep links name (the Mini App resolves it in this list; no route takes a key).
- `src/staging.rs`: staged (memory-only) slash-command flow — `/handoff`, `/btw` + `/prompt_builder` input capture. `/handoff` and `/btw` complete on the staged input with no Accept tap and seed a new topic with `handoff_from` via the shared `seed_new_topic`; only `/prompt_builder` stages an Accept/Discard preview with regenerate, because accepting it runs the prompt in the current thread. The card of a topic-opening command also carries `🎛 Model` (`stg:m`), which edits it into the shared model picker in `ModelPickerScope::Staging` and comes back via `finish_model_pick`; the pick is resolved against `staged_topic_config` (the config the new topic starts with, following the card's current `Continue as:` role) and stored on the session, so it lands on the new thread only (`seed_new_topic`'s `model_override`, which replaces the inherited model) and never touches the current thread. Without a pick, `new_topic_model` is the one rule for both the picker header and the created thread: a source that pinned a model passes it on; otherwise the new topic starts on its own role's default. Staging state is keyed by the alias-resolved thread id (`session_thread_id`), matching message intake. `/handoff` generates its context block first and passes it to `seed_new_topic` as a `record` posted into the new topic (the seed is dispatched synthetically and never appears in chat); on failure the session stays open to retry. `seed_new_topic`'s `profile` argument is the persistent profile the successor starts with. `/handoff` passes `HandoffRole::profile()`: the card's `Continue as: Agent|Orchestrator` button (`stg:r`, beside `🎛 Model`) toggles `StagingSession::handoff_role`, which defaults to the source thread's role (`HandoffRole::of_thread`), so an ordinary thread can hand off into a new orchestrator and an orchestrator into an ordinary agent. Role and model are independent session fields. `Orchestrator` writes the reserved `orchestrator` profile through `record_seeded_thread` and is fail-closed: the handoff errors rather than silently starting a default coding agent. Nothing moves off the source thread — its profile is never written, it keeps its workers and stays usable, so both threads can continue. `/btw` passes `None` and stays an ordinary side thread. `/btw` makes no LLM call at all: its seed is a parent-thread header the new topic's agent resolves with `Read_Thread`, then the labelled question. `/btw` also bypasses the per-topic queue (both the command and the staged question, via `staging::awaiting_btw_input`), so a side question never waits behind the running turn. Bypassed inputs are marked `Message::routed_as_btw_input`, so if the session is gone by the time they land they are answered with a hint instead of falling through to a normal (concurrent) turn; messages older than the command's `message_id` are never taken as staged input. Bot-generated prompts (`Message::synthetic` is set: worker updates) never start or complete a staged command and never skip the queue as `/btw` input. Their synthetic ids count down from `i64::MAX`, so the `message_id` check alone would take a `[worker update]` arriving during `/handoff` as the user's handoff message.
- `src/command_picker.rs`: `/commands` picker — project/context `.md` commands only (picker-only; built-ins live in the native `/` menu)
- `src/commands.rs`: centralized slash-command parsing and matching, including strict `/restart [f|force|--force|q|queue]` parsing (`RestartMode::{Gated,Force,Queued}`); `/restart` bypasses the per-topic queue
- `src/bot/mod.rs`: bot module exports
- `src/bot/context.rs`: shared bot context; also owns per-profile layered configs (`config_for_chat`), the process-lifetime orchestrator route map (owner thread → chat/topic/user for worker completion callbacks), and the thread → pinned-header message map
- `src/bot/queue.rs`: per-chat queueing helpers; topics created from ordinary General messages — and brand-new Threaded Mode DM threads on first sighting — are marked as the persistent `orchestrator` profile before the first turn. The queue worker batches synthetic `[worker update]` prompts: when it starts one it drains every worker update already waiting behind it (`drain_worker_updates`) into the head message's `grouped_messages`, so ingest joins them into a single turn instead of waking the orchestrator once per completion. Draining stops at the first item that must run alone (user message or command); that item becomes the loop's `carry` and runs next, preserving FIFO order. Each drained item still owns a pending slot, so `release_slots` decrements by the batch size — getting that count wrong leaks or prematurely drops the per-key queue entry.
- `src/bot/synthetic.rs`: shared synthetic-message helper (`i64::MAX`-countdown id counter, `build_synthetic_message`, dispatch through the topic queue), used by the orchestrator completion bridge and Mini App artifact feedback. Every synthetic prompt carries its kind in `Message::synthetic`. `SyntheticKind` marks which prompts the queue may batch: `WorkerUpdate` is batched; `ArtifactFeedback` runs as its own turn.
- `src/bot/media_group.rs`: album grouping on the polling loop (`MediaGroups`). Messages sharing chat, topic, sender, and `media_group_id` are held `MEDIA_GROUP_DEBOUNCE` from the first member, then dispatched as one message with `grouped_messages`. A member arriving after its flush opens a new group; recent flushes (at most 2 minutes old, capped at 64 keys) are remembered only to log that as `late_after_flush_ms`.
- `src/intake_log.rs`: privacy-safe intake metadata. One `Telegram message received` line per allowlisted message, stamped before grouping/queue/download (ids, Telegram `date` vs local wall-clock receipt time, poll position, `media_group_id` (verbatim when a short digit string, else an `h:` SHA-256 fingerprint), fixed-vocabulary media kinds, text/caption presence, rich/paid counts, grouping decision); `Media group flushed`, `Message queued`, `Queued message started`, and `Accepted message` carry message ids to join on. Logging authorization (`is_allowlisted`) is `queue::should_process_message` minus its `/whereami` exception; keep them aligned. Never log text, captions, file names/ids, MIME strings, or nested payload bodies here; `emitted_log_lines_carry_no_content` captures real output to check this. Member counts are observed, not Telegram's album size (the Bot API does not send one).
- `src/orchestrator.rs`: orchestrator worker bridge — consumes engine `WorkerManager` `WorkerEvent`s. Workers are **silent**: `Created` opens no topic and only refreshes the owner's pinned card; `Completed` posts a one-line notice in the owner topic (title linked via `handlers::message::worker_link`) and wakes it with a bounded synthetic `[worker update]` turn (several pending updates are merged into one turn by the topic queue). **Legacy mirror topics** from before silent workers are rebuilt at startup from persisted `worker_topic` + `alias_to` meta (`list_worker_topics`) and registered as the worker's `mirror_url`; only for those workers does the bridge still post `📤` orchestrator prompts, one debounced live status line per running turn (with `⏹ Cancel worker` = `wk:c`, worker resolved from the topic alias, and Mini App `💬 Open Thread`), and the final result. Never re-add topic creation here: worker spam in Telegram is what silent workers removed. Routes stay process-lifetime
- `src/handlers/mod.rs`: handler module exports
- `src/restart_queue.rs`: performs queued restarts from any surface (`/restart q`, `zdx service restart --queue`). The worker bridge in `orchestrator.rs` calls `tick` every 3s, but only when `WorkerManager::all_idle()`, then an empty worker-event channel, then an empty chat-queue map all hold. That order is what makes it safe for orchestrators: a worker's run marker ends before its completion reaches the orchestrator, so "no active run" alone could restart between a worker finishing and its `[worker update]` turn being queued, losing the in-memory callback. `tick` then checks `agent_activity` for other surfaces; once nothing is active it restarts the daemon (gated, so a run that starts in between leaves the request pending), clears the request, and exits the bot when `bot` is included. It announces in the requesting thread only when that is an allowlisted Telegram thread. A request already fulfilled by a newer process (a forced or manual restart) is dropped silently, which also stops a restarted bot from firing the same request again. Also owns `attempt_restart`/`RestartAttempt`, shared with `/restart`.
- `src/handlers/message/commands.rs`: slash-command handlers (`/new`, `/model`, `/status`, `/whereami`, `/launcher`, thread/worktree, exit, `/restart`; the `q` mode only writes the shared engine request via `service::queue_restart`) + the provider → model → thinking picker + `ModelPickerScope` (General/Topic/NewThread/Staging)
- `src/handlers/message/launcher.rs`: General-topic thread launcher — bot-visible `[[model_modes]]` filter, `create_topic_with_model`, `create_topic_resuming`, `/launcher` keyboard (`nt:p:{mode}`/`nt:custom`/`nt:resume`) + callback routing; Custom opens the model picker in `NewThread` scope; `🔄 Continue` picker resumes a source thread via `alias_to`; `LauncherMap` + `schedule_repost` keep the launcher as the last message in General (debounced per-chat repost)
- `src/handlers/message/mod.rs`: message intake orchestration + shared turn types (`ReplyContext`, `TurnStatus`, `TurnResult`, `SpawnRequest`, `StatusSnapshot`); `thread_id_for_chat` + `parse_topic_thread_id` (inverse) + `resolve_effective_thread_id` (follows one `alias_to` hop so resumed topics load/persist to the source thread); `mini_app_base_url`; re-exports the keyboard builders
- `src/handlers/message/turn.rs`: agent turn lifecycle (`run_agent_turn`, spawn/stream/finalize)
- `src/handlers/message/status.rs`: turn status setup/update/cleanup, the status keyboard (Cancel + Mini App `Open Thread`), and status-message formatting (usage, pricing, context)
- `src/handlers/message/thread_header.rs`: first-message topic status card, Mini App/refresh keyboard, and silent pinning; records the posted header per thread on `BotContext` so `refresh_thread_header` can re-render it in place (the worker bridge does this on worker events for orchestrator cards)
- `src/handlers/message/response.rs`: final response sending and delivery truth. `send_final_response` writes a pending `ThreadEvent::Delivery`, runs `deliver_reply` on the `reliable()` client (one captioned message only when text + a single photo, voice note, or audio file fit the 1024-char caption, measured with `markdown::visible_utf16_len`; otherwise the text (split by `markdown::split_telegram_html` into parts within `MAX_MESSAGE_LEN`, tags counted; one `DeliveryItem::text_part` per part; follow-ups on the last part), then every file as its own message (an HTML file with an `Open artifact` link as a `file_card` text message, `link_only` item, never uploaded) — documents are never merged into a rich message or captioned with the reply, because every document of a multi-document rich message was observed to open the same file; an unabsorbed flood refusal stops the remaining items; ambiguous failures are `unknown` and never resent). Each file message carries its own `↗ Open artifact` URL button (`ReplyFile::open_url`, built by `artifact_link`: `{mini_app_url}?startapp=a_<key>_<topic thread>`, key from `zdx_engine::core::artifacts::artifact_key`, thread = the receiving topic's session id from `thread_id_for_chat`, not the alias-resolved one, so Mini App feedback goes back to that topic; no button without a configured Mini App, when the value would exceed 64 characters (a conservative local limit, not a documented `startapp` limit), or when `artifacts::lexical_path_is_physical` says the listed path is another file than the one sent); a captioned file carries it above the follow-ups. Buttons ride on the send itself, never on a later edit, writes the outcome under the same record id, and posts one `user_summary` on a partial delivery. Only an invalid reply target (`is_invalid_reply_error`) is retried without `reply_to`. Every answer gets a trailing `↗ Open thread` Mini App deep link (`{mini_app_url}?startapp={thread_id}`) via `append_thread_link`, skipped when the Mini App is not configured for the chat; orchestrator answers also get one `🛠 <title>` link per worker the turn created or messaged, pointing where `worker_link` says (Mini App deep link; a legacy mirror topic when the worker still has one) (`TurnResult::touched_workers`, collected from `Create_Thread`/`Send_Thread_Message` results in `turn.rs`). Plain-text answers are sent through the `*_without_preview` client wrappers so that link does not render a preview card (a rich message has no preview option); other message paths keep previews.
- `src/handlers/message/media.rs`: `<media>` routing parse (paths cleaned by the engine's `artifacts::clean_media_path`, the same rule the artifact projection uses) + path classification (image→`sendPhoto`, `.ogg/.oga/.opus`→`sendVoice`, `.mp3/.m4a/.wav`→`sendAudio`, else `sendDocument`)
- `src/ingest/mod.rs`: Telegram message parsing + attachment loading. `replied_to` carries the text (or the user's quote, `Message::quote`) of an explicitly replied-to message; a reply to the forum topic's creation message (id = topic id), which Telegram sets on every topic message, is not one. Message text comes from `Message::plain_text()`, which falls back to `rich_message` — Bot API 10.1 rich messages (structured lists/headings/tables) leave `text` unset, so reading `text` directly drops the whole message silently (SPEC §19). Photos and `image/*` documents go through `load_image`: the original is always saved, and `prepare_inline_image` sends the model a `downscale_to_fit` copy (`INLINE_IMAGE_EDGE`/`INLINE_IMAGE_BYTES`) or a `SavedOnly` reason with `ask_media` guidance. Load failures become `IncomingMessage::notices` via `push_attachment`; return an `AttachmentNotice` error for a specific sentence, and never put the raw error in a notice, since download errors embed the bot token in the URL. `download_file_bytes` retries `getFile` + fetch on a transient error (`is_transient_download_error`: a `TelegramTransportError` or HTTP 5xx; a Telegram refusal is not retried); a transient failure that survives every try aborts the whole message as `DownloadUnavailable` instead of a notice, so no turn runs and the handler offers a retry. `Message::local_attachments` (files a surface already saved on this host, e.g. Mini App feedback) load through the same paths: `load_local_image` → `prepare_inline_image`, `load_local_audio` → transcription; an unreadable file becomes a notice. Their `label` (`Voice note 1 for note 2`) rides on `IncomingAudio`/`IncomingImage` and `build_user_text` prints it next to the file, so per-note media stay associated. Video, video note, animation, and `video/*` documents are listed by `video_attachments` and loaded by `load_video` (limit = `zdx_engine::media::MAX_INLINE_BYTES`, so every saved video fits `ask_media`); Telegram duplicates an `animation` into `document`, so the generic document branch skips both that twin and `video/*` documents.
- `src/agent/mod.rs`: thread log + agent turn helpers (`load_thread_state` returns replay's `trailing_note`, delivery problems and posts by other runs, and `record_user_message` puts it first in the new user message so live equals replay; `build_user_text` puts a `<reply_to>` block from `IncomingMessage::replied_to` before the user's text); orchestrator prompt extras (`telegram_workspaces_block` lists bound profiles plus each root's project skills via `workspace_skills`, the `$ZDX_HOME/orchestrator.md` overlay)
- `src/telegram/mod.rs`: Telegram API client + tool wiring (HTML send/edit/caption fallback ladder: HTML → `html::sanitize` retry → plain text). Every call goes through `call`: the per-chat `ChatGate` (shared rules in `zdx_engine::telegram::flood`), typed errors, and one log line per attempt. Handles: default `Immediate` (skips a chat in flood wait, never waits — required on the polling loop and the worker bridge), `paced()` (waits, at most the 2-minute retry deadline; status messages and the status delete), `reliable()` (waits + flood-refusal retries; reply text, files, delivery summary). The gate is per client instance, so tests that need shared state must reuse one client. Check Telegram refusals with `api_error_description`/`is_invalid_reply_error`, not by matching the error string. `src/telegram/fake.rs` is the scripted fake Bot API for client tests (unscripted, it refuses what Telegram refuses: `sendMessage` text over 4096 characters and reply targets that quote an internal synthetic id); `topic_link(chat_id, topic_id)` builds the `t.me/c/<internal_id>/<topic_id>` form for supergroup topics (shared by the Mini App thread list and worker mirrors)
- `src/telegram/html.rs`: Telegram HTML repair pass — escapes stray `<`/`&`, drops unsupported tags/entities, balances unclosed or crossed tags
- `src/telegram/markdown.rs`: model-text Markdown → Telegram HTML edge converter + entity-safe visible-character truncation + `split_telegram_html` (long reply text → message-sized parts, tags reopened per part)
- `src/telegram/rich.rs`: incoming rich messages (Bot API 10.1) → Markdown-ish plain text. Blocks stay `serde_json::Value`: Telegram keeps adding block/text types, and an unknown one must degrade to its nested text rather than fail the update or lose the user's words.
- `src/telegram/types.rs`: Telegram API DTOs
- `src/topic_title.rs`: async LLM-based topic title generation
- `src/transcribe.rs`: audio transcription helper
- `src/types.rs`: bot message/media types

## Conventions

- Keep Telegram API DTOs and request behavior inside `src/telegram/`.
- Keep orchestration in handlers; move reusable logic to smaller modules.

## Checks

- The Mini App must be built before any cargo command touches this crate: `just web-build` (rust-embed reads `apps/web/dist` at compile time). `just build-release` and CI do this automatically.
- Follow the root verification rules. Scoped tests: `cargo test -p zdx-bot --lib --bins --tests`.

## Maintenance

- Bot behavior contract changes: update `docs/SPEC.md` as needed.
