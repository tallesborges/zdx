# zdx-engine development guide

Scope: core runtime engine — config, agent orchestration, tools, prompt/context assembly, and shared registries.

## Where things are

- `src/lib.rs`: engine crate exports
- `src/test_support.rs`: shared test environment RAII helper (`TestZdxHomeGuard`) for unit tests needing isolated `ZDX_HOME` state
- `src/providers.rs`: re-export of `zdx_providers::*`
- `src/audio/mod.rs`: shared audio module exports
- `src/audio/speak.rs`: shared text-to-speech (TTS) synthesis helpers (OpenAI/Mistral); default OGG/Opus output via ffmpeg transcode with MP3 fallback
- `src/audio/transcribe.rs`: shared audio transcription helpers (OpenAI/Mistral via `/audio/transcriptions`; xAI Grok STT via `/stt`; ElevenLabs Scribe via `/v1/speech-to-text` with `xi-api-key`). Mistral gets the custom vocabulary as `context_bias`, capped per provider (`vocabulary_limit`). Voxtral Transcribe 2 rejects the whole request when one entry has a space or comma, so `accepts_phrases` gates phrases by model and other entries are skipped, never sent
- `src/audio/vocabulary.rs`: custom transcription vocabulary (SPEC §20): global `$ZDX_HOME/vocabulary.txt` plus optional extra files, case-insensitive dedupe (first spelling wins). Read on every call, no cache
- `src/agent_activity.rs`: active-run registry (ephemeral marker files for agent turns: phase, current tool round incl. finished calls until the next round, activity time, 5 s heartbeat, `birth_id` process start time; `list_active` drops markers whose PID is gone or reused, never by heartbeat age) and `RunRecord::status`, the shared `RunStatus` every surface shows
- `src/background_activity.rs`: background-process registry — durable marker files under `~/.zdx/run/background/` for background jobs (`kind`: Bash `command`s, detached or adopted, and background `subagent`s, which also record `child_thread_id`); identity-guarded (`pid`+birth-time+`pgid`) kill defends against PID reuse; exited-tombstone + age prune
- `src/job_scheduler.rs`: the scheduled scheduler's context (the running record `run/scheduler.context.json` the Go scheduler writes, else the installed launchd plist, else unavailable with a reason) and job settings resolved with it (`resolve`). Surfaces that show scheduler settings use this, never their own root.
- `src/jobs/`: the Rust side of jobs (see `docs/ARCHITECTURE.md` § Jobs Scheduler; the Go package `apps/shared/jobs` owns job files, schedules, state, and the scheduler). `mod.rs`: the shared resolver over a `JobSpec` of declared values (`resolve_run`, `resolve_run_settings`, `resolve_run_from` with an explicit inherited context). `records.rs`: the read-only view of `jobs_runs.jsonl`. `history.rs`: `recent_runs` (from `jobs_runs.jsonl` only, so unrelated threads never count; attempts grouped by `run_id`, legacy lines by thread; posts from `core::posted` link files, answers counted from the conversation thread, skipped over 4 MiB) and `prompt_section`, the previous-runs block a run gets. Surfaces do not re-derive model or root.
- `src/config.rs`: config loading + paths (embeds `zdx_assets::DEFAULT_CONFIG_TOML`). Owns model selection: `apply_model_selection` / `apply_thread_model_override` resolve `mode:<name>` against the config's modes and record `model_mode`, and fail with `UnknownModeError` for an undefined mode (explicit selections must surface that, never run the default); `apply_model_spec` is the lenient form for already-validated selections. Subagent layers (frontmatter, overrides, per-call model, persistent profiles) go through `subagents::apply_subagent_model`, which is strict the same way. Surfaces persist `model_selection()` (the reference or the concrete spec), never the resolved `model` of a mode selection
- `src/custom_commands.rs`: custom slash command discovery + frontmatter parsing (`<ZDX_HOME>/commands` + ancestor/current `.zdx/commands`, plus bundled commands from `zdx_assets::bundled_command_assets()`)
- `src/followups.rs`: shared `<followups>` suggestion-block parsing (surfaces strip + render their own way)
- `src/models.rs`: model registry for model picker (embeds `zdx_assets::DEFAULT_MODELS_TOML`); also resolves `ask_media` audio declarations (`model_audio_input`, `declared_audio_models`) from the embedded then user `model_overrides.toml`, never from `models.toml`
- `src/mcp.rs`: MCP config loading, server discovery, helper workspace/runtime, and MCP tool-call execution helpers
- `src/prompts.rs`: prompt template helpers/re-exports of `zdx_assets` prompt constants.
- `src/skills.rs`: skills discovery + parsing (materializes bundled skills from `zdx_assets::bundled_skill_assets()`); `load_configured_skills` (the run's configured catalog, shared by prompts and tools) and `SkillScope`/`skills_in_scope` (what the skill tools may reach)
- `src/subagents.rs`: named subagent discovery + parsing (built-in subagents come from `zdx_assets::{EXPLORER_SUBAGENT,ORACLE_SUBAGENT,HTML_ARTIFACT_SPECIALIST_SUBAGENT,ORCHESTRATOR_SUBAGENT}`; `orchestrator` is reserved — user/project files cannot define it, and `load_builtin_orchestrator()` loads it directly from the embedded asset; `load_persistent_profile` resolves a persistent-profile name (built-in orchestrator or a subagent file, tools required) and `apply_persistent_profile_model` its model chain; `background_commands` defaults to off)
- `src/images/mod.rs`: shared image utilities module exports
- `src/images/path_mime.rs`: path normalization + extension MIME helpers
- `src/media.rs`: one-shot media understanding (audio/video/PDF/image + prompt → text); shared by the `ask_media` tool and `zdx ask-media`. Gemini takes every type; other providers take audio only, when the provider has audio settings (built-in: `config::effective_provider_audio`, `[providers.<name>.audio]` over the embedded `zdx-assets/audio_providers.toml`, field by field; custom: `[providers.custom.<name>.audio]`, chat-completions only; no per-provider branch, only credential resolution differs) and the model has `input_audio = true` in an override file (`models::model_audio_input`). `zdx_providers::audio_chat` sends the request. Audio in a format the model does not take is converted with `ffmpeg` to mono PCM WAV at the decoder's sample rate
- `src/orchestration/`: the engine service (overview: `docs/ARCHITECTURE.md`, Engine Service + Worker Threads; contract: SPEC §18). `runtime.rs`: `Engine` (worker manager, per-thread FIFO with worker-update batching, delivery of each worker result to the thread that queued it, delivery holds, cancel, settlement answered on the worker-event task, injectable `TurnRunner`). `prompt.rs`: persistent-profile turn setup (profile, model chain, surface layer, Telegram Workspaces block, overlay). `updates.rs`: `[worker update]` text and `record_user_input`. `protocol.rs`/`server.rs`/`client.rs`: the Unix-socket protocol (`$ZDX_HOME/run/engine.sock`, `0600`, peer uid checked). `ensure_direct_run_allowed` is the one-writer guard; `run_turn_inner` also refuses non-service turns on a persistent-profile thread (`ACTIVITY_KIND`).
- `src/orchestration/view_bodies/`: the read-only view bodies (the exact JSON of the Mini App API), as plain async functions on `EngineViews`; `orchestration/views.rs` adapts `ViewRequest`s to them (`impl ViewProvider for EngineViews`). The service's views (`zdx engine serve` installs `EngineViews::in_service(root, manager)`; the gateway's Mini App routes read them) and `zdx views` (`EngineViews::client(root)` when the service is stopped) call these, so none of them needs the built Mini App. The root is explicit, passed by the caller: the fallback root `thread_root` reports and the config the dashboard and usage read. Errors are `ViewError`s (`ErrorCode` + the route's exact text); a surface maps the code to its status. Caches and permits live on the instance (clones share them). `EngineViews::thread` answers `delivering: false`; the gateway sets it from its own delivery tracker. Socket artifact requests check the path before the thread; the HTTP routes check the thread first. The dashboard views are separate: `monitor_snapshot` (built off the async hot path, uncached; its `subscriptions` is always `[]`, `pending`, no age) and `active_agents` (run markers, read fresh). The gateway composes `/api/monitor` from them and owns its caching. Rust has no quota code: the gateway, the monitor, and `zdx quota` read quotas with the shared Go package (`apps/shared/quota`); the former `subscription_quotas` view is refused as an invalid request. `thread_root` (`view_bodies/thread_root.rs`) names the thread a Git route means (`active` resolved, one `alias_to` hop) and its stored root, both roots absolute; the gateway serves `/api/git*` in process with the Go `apps/shared/gitview` on it. Rust has no Git views: the former `git_status`/`git_scope`/`git_diff` ops are refused as invalid requests (socket and `zdx views`), and Git behavior (scopes, the main-branch base, revision and path checks) lives only in `apps/shared/gitview`. `/api/threads` lists the 50 most recent top-level threads (`?kind=workers`: only workers, via `thread_persistence::list_recent_workers`), limited in SQL, each carrying an `is_worker` flag (`ThreadSummary::is_worker`) and a `t.me/c/<internal_id>/<topic_id>` link when the thread id encodes a supergroup topic. `/api/threads/{id}/workers` lists an orchestrator's workers by merging two sources that are **not** equivalent: live `WorkerSnapshot`s read from the engine service (`LiveWorkers` on `EngineViews`, blocking client calls on the blocking pool; an unreachable service reads as no live workers), and children recovered from `thread_meta.parent_thread_id`. The persisted half restores *discovery* only — a recovered row is returned with `live: false` and `status: "unknown"` rather than being reported as settled, because runtime state does not survive a service restart. Persisted children are filtered by `ThreadSummary::is_worker`: the same parent link is used by subagent and helper runs, which are not workers. The same merge feeds `ThreadResponse.worker_count`, which gates the Mini App's Workers tab, alongside `parent_thread_id`/`parent_title` for the breadcrumb out of a worker thread. Both the workers route and the lineage lookup resolve one `alias_to` hop first (`resolve_alias_id`, same rule `thread_root` uses): Mini App deep links carry the *topic session* id, and a worker mirror topic is an alias whose own thread file has neither lineage nor workers, so skipping the hop makes a worker opened from its mirror look parentless. `/api/threads` additionally returns a per-row `workers` roll-up for orchestrators, built from `thread_index::worker_counts_for_parents` — one indexed `GROUP BY` over just the ids on the page being rendered, not a corpus scan — unioned with live statuses from the service (`LiveWorkers::statuses_by_owner`). `failed` is its own bucket in that roll-up rather than part of `settled`, and `total` takes the larger of the live and persisted counts because the index syncs on a freshness window and can lag a just-created worker.

  - Transcript tool items: `project_thread` (`threads.rs`) pairs each `tool_result` with its `tool_use` and attaches `view` from `zdx_types::tool_view` (display projection); `attach_live_run` attaches an input-only view to `tool_running`, and a `tool_use` with no result in the thread (interrupted) gets one too. `output` stays the raw envelope for the app's JSON view. No tool-specific display logic lives here.
  - Usage (`EngineViews::usage`, `GET /api/usage?days=N`): default `usage_report::DEFAULT_DAYS`, 1-365, else `Invalid` (`400`); a thin adapter over `core::usage_report::report`, cached per window for `MONITOR_CACHE_TTL` under one lock held across the build, so concurrent requests share one usage-cache sync. The monitor snapshot does not carry usage.
  - Workspaces (`GET /api/workspaces`): a read-only, uncached adapter over `workspace_config::report(Some(root))` plus `global_report()`: every workspace with its model settings, origin layers, and inherited fallbacks, and the global file's own settings. No write route exists; writes go through `zdx config set-setting|reset-setting`.
  - Trajectory (`GET /api/threads/{id}/trajectory`): a thin adapter over `core::thread_trajectory`; it adds bounded live-tool marker snapshots but owns no timing, ranking, overlap, or legacy-data semantics.
- `src/orchestration/` chat-surface operations (wire: SPEC §18 "Chat-surface operations"): `thread_ops.rs` (resolve, update, record delivery, reset), `feedback.rs` (`feedback_submit`; in-flight guard and decode slots on the `Orchestrator`), `helpers.rs` (`generate`, `btw_seed`, `topic_start`), `catalog.rs` (picker, launcher, resumable, resume source, thread status, custom commands, `set_chat_model`; the bot calls the same topic-config, selection-label, mode-filter, launch-config and selection-source functions). Holds are owner-bound (`HolderRef` tokens; `orphan_action` decides what a vanished holder's hold becomes).
- `src/core/chat_turn.rs`: chat input composition (`compose_user_text`), inline image preparation, reply parts and send types; shared by the bot and the socket.
- `src/core/thread_lease.rs`: the per-thread run lease (one writer of a thread's turns across processes; `AgentOptions::run_lease` carries it into a turn).
- `src/core/topic_start.rs`: the starting model of a seeded (`/handoff`, `/btw`) topic; refuses creation when it does not resolve.
- `src/telegram/photo.rs`: photos fitted to `sendPhoto` limits (shared by the bot and `prepare_photo`).
- `src/pidfile.rs`: PID file management
- `src/proc_liveness.rs`: process liveness and identity primitives shared by the PID file, agent-activity, and background-process trackers
- `src/service.rs`: launchd-backed control for the long-lived `bot`/`scheduler`/`engine` services — plist rendering, `install`/`uninstall`/`start`/`stop`/`restart`, and combined launchd+PID-file `state()`. `ensure_restart_allowed` is the one guard for `restart_many` and `stop`: active agent runs anywhere, plus, when the engine service is a target, its own settlement (asked over its socket; it owns queued worker prompts, pending results, and queued or held turns that are not agent runs yet). Also owns the queued restart: one persisted request at `run/restart-queue.json` (`queue_restart` merges into a pending one and refuses unless a supervised bot is running to perform it; `QueuedRestart::is_fulfilled` compares service PID-file start times against `requested_at`). The bot agent runs the Go gateway `~/.local/bin/zdx-go gateway` (`default_program_for`, `default_go_program`; `check_program` refuses a `zdx` bot program, and the read-only `gateway preflight` must report ready first); the scheduler and engine run `~/.local/bin/zdx`. Never `current_exe()`, so restart picks up the installed binaries. A restart whose installed command arguments are not the current ones (`InstalledLaunch::is_outdated`, e.g. the old `zdx-gateway --root ROOT bot`) installs the service again with its default program instead of `kickstart` (`outdated_definition`); `run_queued_restart` cannot do that for the bot it runs in, so it keeps the bot up and says to run `zdx service restart bot`. Every plist sets `ZDX_BIN` to the installed `zdx`. Agents are launched via `zsh -c 'exec …'` so `~/.zshenv` (provider API keys, PATH) is sourced. Plists set `ZDX_SERVICE_SUPERVISOR=launchd` and capture output to `~/.zdx/run/logs/{name}.{out,err}`. macOS-only.
- `src/telegram.rs`: outbound Telegram Bot API calls (create topic, send message, send document); shared by the Telegram tool and `zdx telegram`. Sends return a `SentMessage` receipt (Telegram's `message_id`, topic, `t.me/c` link from `message_link`). Owns `conversation_thread_id` (the bot's `telegram-<chat>[-topic-<topic>]` thread id, inverse `parse_topic_conversation_id`), `topic_link`, and `record_post`, which both surfaces call after a delivered send to write a `ThreadEvent::Posted` into the destination conversation (one `alias_to` hop; skipped for the caller's own thread). Retries explicit flood refusals per `flood::RetryPolicy::IMPORTANT`; no pacing gate (it runs outside the bot process).
- `src/telegram/flood.rs`: Telegram flood control for `TelegramOutbound`: typed errors (`TelegramApiError`, URL-free `TelegramTransportError`), `classify` (flood wait / rejected / not sent / unknown), `RetryPolicy`, `bot_identity`, and `log_call`. No pacing: per-chat pacing lives in the Go gateway (`apps/gateway/internal/telegram/pacer.go`). Every network path must surface failures as these types: an untyped error classifies as "not sent".
- `src/tracing_init.rs`: tracing setup
- `src/workspace_config.rs`: shared workspace model-settings view — workspace list (Telegram profile `cwd`s used as-is + the caller's root resolved to its project root), per-setting effective value + origin layer (`default`/`global`/`workspace`/`ancestor`) + inherited fallback, a `Scope` (global alone or one workspace's chain; its `file()` is what edits write, and `overlay_is_global` workspaces write the global file), `reach` (which listed workspaces read a file's value per key; `Reach::skip_groups` groups the skips by the layer that sets the key), targeted `set_setting`/`reset_setting` on one layer, and `change_setting` (`parse_value`, then the change applied to a temp copy and the scope's layers loaded with it before the real write; dry run, reach, and the setting after). Backs Monitor Config, `zdx config workspaces|set-setting|reset-setting`, and `/api/workspaces`. Writers reuse `Config::*_to` (whose `layer_document` seeds the template only for the global file, so overlays stay minimal) and `Config::unset_layer_key`.
- `src/zdx_context.rs`: shared `{{ZDX_CONTEXT}}` block that tells helper subagents (handoff, tldr, prompt-builder, `Read_Thread`), which run without a system prompt, about installed subagents and skills

### Core runtime (`src/core/`)

- `core/mod.rs`: core module exports
- `core/events.rs`: agent event types for streaming
- `core/context.rs`: project context loading (`AGENTS.md`/`CLAUDE.md`, memory)
- `core/interrupt.rs`: signal handling
- `core/agent.rs`: agent loop + event channels. Owns the stalled-stream limit (`stream_idle_timeout_secs`): one no-progress budget per provider request, covering the wait for the stream to open and the gaps between non-`Ping` events, measured on Tokio's clock so tests use paused time. A stall is a retryable `Timeout` provider error, so it goes through the normal retry gate.
- `core/delivery.rs`: delivery records for replies sent to chat surfaces (`DeliveryRecord`/`DeliveryItem`, pending/sent/failed/unknown; reply text split over several messages is one item per part, `TextPart`; `link_only` marks a file delivered as a Telegram file card, not uploaded), persisted as `ThreadEvent::Delivery`; owns the model note (replay prepends it to the next user message via `ThreadReplay::trailing_note`), the user summary, and the transcript/Mini App notice text. Display paths skip records superseded by a later one with the same id (`thread_persistence::superseded_deliveries`).
- `core/posted.rs`: messages another run posted into a chat conversation (`PostedMessage`, persisted as `ThreadEvent::Posted` by `telegram::record_post`); owns the model note (replay prepends it to the next user message, after the delivery note, via `ThreadReplay::trailing_note`), the transcript/Mini App notice, and the `read_thread` text. The sender's `context` is bounded (`MAX_CONTEXT_CHARS`) and labelled as data. Also the per-sender link files (`PostLink`, `$ZDX_HOME/state/posted/<sender thread>.jsonl`, written by `record_post`), which let a job's later runs find where an earlier run posted without scanning threads.
- `core/artifacts.rs`: shared thread artifact model — artifact-dir scan merged with transcript `<media>` refs (deduped), preview kinds, opaque per-file `artifact_key` (deep links), download path guard
- `core/artifact_feedback.rs`: user annotations on an artifact (HTML, or PNG/JPEG/WebP images) → validated, version-checked (SHA-256 of the annotated bytes; `allow_stale` sends a changed file explicitly) bundle under `$ZDX_HOME/artifact-feedback/<thread>/<submission_id>/` plus the agent prompt with per-note media labels. Owns the limits and the payload shape every surface sends, including the HTML targets (element, text quote with prefix/suffix and its holding element, drawing, page) and `carried_from` on notes moved from an earlier version. The artifact is read once (`read_version`): the hash and the annotated-version copy come from the same bytes. Page-captured strings are untrusted: bounded, control characters stripped, JSON-quoted in the prompt. Audio is checked by container magic (EBML/`ftyp`/Ogg/MP3/WAV), images by `infer` (PNG/JPEG/WebP) and by header dimensions (`MAX_IMAGE_PIXELS`) before anything decodes them. Retry identity is a fingerprint of the caller's sender/destination `binding` plus content (viewport excluded): a bundle with the `queued` marker and the same fingerprint is `Duplicate` (checked before the artifact, which the agent may have edited since), another fingerprint is `IdConflict`, no marker means abandoned and is replaced. Surfaces write the marker with `mark_queued` right before queueing. Callers serialize saves per submission id. `core/artifact_feedback/canonical.rs`: the canonical copy of an image artifact — the one frame for preview, coordinates, and model input. Large originals are shrunk automatically; `MAX_SOURCE_BYTES` (25 MiB, from the file length before reading or hashing: `check_source_size`) and `MAX_SOURCE_PIXELS` (40 MP, from the header before decoding) only bound what is read and decoded, and are image-annotation limits only (attached note images keep `MAX_IMAGE_PIXELS`/`MAX_IMAGE_BYTES`, HTML keeps `MAX_SNAPSHOT_COPY_BYTES`). `cached` applies the same policy to cache records (`source_bytes` is required, so records from before the limits are ignored), so a stale send never draws on a copy made under other limits; output pixels did not change, so `CANONICAL_VERSION` stays. Decodes within the decoded-output limit (`MAX_DECODED_BYTES` bounds the output buffer, not peak memory: decoder working buffers can be about 3× that for some encodings) under a process-wide gate (`MAX_NORMALIZATIONS`, shared by every caller, slot held on the blocking thread until the decode and shrink end; `FeedbackError::Busy` after 60 s; `test_hooks::pause` lets tests hold a slot), reads EXIF orientation the same way for every format (WebP with or without the `Exif\0\0` header; unreadable EXIF refused), shrinks with a box filter (`thumbnail_exact`: no full-width float intermediate, which a separable filter would allocate) before turning (no full-size rotated buffer), encodes PNG only when transparency is used (else a JPEG ladder, then halving) within `CANONICAL_MAX_BYTES`, and caches by source hash (always computed from the bytes: `canonical_from_bytes` hashes them itself) + `CANONICAL_VERSION` (bump it whenever output pixels change: drafts on old copies then go stale instead of moving). The cache is content-addressed; callers resolve the artifact for the thread first (`canonical_for_artifact`). `core/artifact_feedback/image_marks.rs`: draws marks on the copy at its own size and format within `MARKED_MAX_BYTES` (the bot's inline limit, so the model gets those bytes unchanged) plus per-mark close-ups; `check_cost` bounds the disc-stamping of drawn lines (`MAX_DRAW_OPS`, about 0.3 s release) before anything is drawn, since point limits alone allow long lines.
- `core/fts_query.rs`: shared FTS5 `MATCH` builder, so thread search and memory search interpret a query the same way
- `core/handoff_generation.rs`: LLM-based handoff context generation and the header-first `/handoff` and `/btw` seeds (source header, labelled user message, labelled generated background; served by the `generate` op). The source thread is rendered with `thread_persistence::format_handoff_transcript` (user and assistant messages only; no reasoning or tool calls/results, which stay recoverable through the seed's `read_thread` pointer); `read_thread` and TLDR keep `format_transcript`.
- `core/media_fallback.rs`: image fallback for models with `input_images = false` — swaps user/tool-result image blocks for a note pointing at the `ask_media` tool, applied per model turn in `core/agent.rs`
- `core/prompt_builder_generation.rs`: LLM-based prompt-builder generation (the `generate` op)
- `core/recency.rs`: shared recency decay applied to search relevance scores (`thread_index` and `native_memory`)
- `core/native_memory.rs`: native SQLite-backed memory index/search over exported thread Markdown, Notes, and Calendar; owns `$ZDX_HOME/cache/memory.sqlite` and native `zdxmem:v1:*` docids. Includes the opt-in hosted embedding layer (`[memory.embeddings]` profile, budgets, `(input_hash, profile_fingerprint)` vector storage, vector/hybrid retrieval with RRF fusion); agent searches never trigger corpus embedding.
- `core/thread_index.rs`: derived thread cache at `$ZDX_HOME/cache/threads.sqlite` (metadata, export dirty state, FTS over title + user/assistant text, tool-call rows); serves `list_threads()`, `search_threads()`, `search_thread_tools()` with a raw file-scan fallback. **The sync split is load-bearing:** `SyncScope::Meta` reads one line per changed thread; `SyncScope::Full` re-reads and re-tokenizes each changed transcript. Listing, lineage and lookup paths must take `Meta`; only search and browse take `Full`. Routing a metadata reader to `Full` puts corpus re-tokenization back on the Mini App hot path (measured 7.7s with 20 active threads). Details are in the module docs.
  - `indexed_thread_files()` publishes each thread's `(mtime_ns, size)` change token after a `Meta` sync, so other derived caches (`usage_stats`) never `stat()` the corpus themselves.
- `core/steer.rs`: steering (SPEC §21): `SteerInbox` (in memory), `SteerFile` + `append_steer_line` (a worker child's file), `SteerSource`, `CloseOnDrop`. The agent loop takes steers only after a whole tool round (`process_tool_turn`) and closes the source before the terminal event; owners drain unread items with `drain_unread`.
- `core/subagent.rs`: child `zdx exec` subagent runner. Child runs persist their own thread JSONL tagged via `ExecSubagentOptions::thread_origin_kind`/`thread_parent_id`/`thread_subagent_name` (so their usage is captured by `usage_stats`); tagged threads are hidden from default listings. `ExecSubagentOptions::thread_id` runs the child against an explicit existing thread (`--thread`, resumable workers). Unix children use the shared `zdx-tools` lease supervisor so cancellation, future drop, or owner death TERM→KILLs the group and reaps the target. `spawn_exec_subagent` and `read_stdout_events` are shared by the blocking path and background subagents. A blocking call waits for the child to *exit*, not for its final answer.
- `core/thread_export.rs`: clean Markdown transcript exports derived from saved thread JSONL
- `core/title_generation.rs`: LLM-based title generation (the `generate` op: bot and chat TUI)
- `core/tldr_generation.rs`: LLM-based thread TLDR/recap generation (the `generate` op)
- `core/thread_persistence/`: thread persistence (JSONL per thread; `persist`, `replay`, `search`, `storage`, `format`, `event`). Every write to a thread file goes through `Thread` (or `import_runner_events`, the external runner's append) and holds `ThreadFileLock` (sidecar `flock` under `$ZDX_HOME/run/thread-locks/`, shared across processes); a new write path that skips it reopens the lost-append race between the bot's meta rewrites and the engine service's appends (`concurrent_appends_survive_metadata_rewrites`). Never lock the thread file itself: rewrites replace its inode, and `ChildThreadLock` holds it for a child's whole run. `list_threads()` hides child runs (any thread with `Meta.origin_kind` set — subagents/helpers); `list_all_threads()` includes them. Usage stats scan raw files (`list_thread_files`) so they still count child runs.
- `core/thread_trajectory.rs`: UI-agnostic, serde-serializable per-thread trajectory projection shared by CLI JSON/text, Monitor, and the Mini App API; owns span pairing, exact interval placement/overlap, bottleneck ranking, live snapshots, and legacy uncertainty
- `core/usage_stats.rs`: usage/cost aggregation over saved threads, backed by the disposable cache `$ZDX_HOME/cache/usage-v3.sqlite` (see `docs/ARCHITECTURE.md`, Usage Accounting). Keep the caller's `default_model` out of cached rows: callers with different configs share the cache, and a config-dependent key makes them wipe it for each other (verified 2026-10-14: a full 21k-thread rescan, about 70 s, on every Mini App monitor refresh). Parse transcripts outside the cache's write lock and keep write transactions short: holding the lock across a scan made concurrent callers fail with `SQLITE_BUSY` and fall back to a full uncached scan (verified 2026-10-14). It learns which threads changed from `thread_index::indexed_thread_files()`; do not add a second directory walk on the dashboard path. The walk stays only as a fallback (tests, unavailable index).
- `core/usage_report.rs`: windowed usage report shared by `zdx stats` and the Mini App (`GET /api/usage`): totals plus splits by project and run kind (agent, profile, worker, subagent, helper). Attribution comes only from thread-index lineage; a subagent or helper counts toward its nearest non-child ancestor's root. Unknown threads stay unknown. Tokens are recorded usage, not provider quota.
- `core/workers.rs`: in-memory `WorkerManager` for persistent-profile threads, owned by the engine service (overview: `docs/ARCHITECTURE.md`, Engine Service + Worker Threads). Invariants:
  - `all_idle()` and `idle_for_requester()` rely on each worker sending `Completed` under the same lock that settles its status (and clears `running_requester`). Keep them together; the service's settlement check (and through it the bot's queued restart and `send --wait`) depends on it.
  - Per worker, events arrive as `Created` → (`Prompted` | `Activity` | `QueueChanged`)* → `Completed`; `QueueChanged` (waiting prompts removed without running) is sent after the state change so the service rechecks settlement; the default runner drains all `Activity` before the turn's `Completed`.
  - Completions route by `QueuedPrompt.requester_thread_id` (captured at enqueue), never by the mutable `WorkerState.owner_thread_id`, which only drives listings and cards.
  - `thread_persistence::is_worker_lineage` and its SQL twin `thread_index::WORKER_SQL` must stay in step (`worker_filter_matches_only_worker_lineage` checks this).
  - Resumes (`send_message`, `enqueue_from_topic`) re-read the worker thread's persisted root **and** model override and pass the override as `-m`. A `mode:<name>` override is passed as the reference, so the child resolves it against the root's config layers for that turn (the external runner resolves it on the host, `external_worker::resolve_model`). The child `zdx exec` also falls back to the thread's stored override when no `-m` is given.
  - Steering (`steer()`): the decision, the steer-file append, and any fallback enqueue happen under the state lock; settlement of a turn's steers (`settle_steers`) runs under the lock that publishes `Completed`, before idle. A steer is queued again only when the child's closing marker arrived (`WorkerSteer::record_closed`); without it, unread steers are `uncertain` and never re-sent. Only local runners take steers.
  - All state is process-lifetime; thread JSONL survives a restart.
  - `from_config` selects the runner (`[workers]`, read once at service start). Only the local runner requires the worker root to exist on this host (`worker_root`); the external runner takes an absolute host-side identity.
- `core/external_worker.rs`: the external worker runner (Unix; contract SPEC §18 External worker runner). Writes the per-turn job directory under `$ZDX_HOME/run/workers/`, runs `<command> run <request.json>` under the process supervisor, relays stdout as activity only, decides the turn from `result.json`, imports the returned transcript with `thread_persistence::import_runner_events`, and calls `<command> cleanup` when no result exists. Tests drive it with a fake shell launcher.
- `core/worktree.rs`: git worktree management helpers

### Tools (`src/tools/`)

- `tools/mod.rs`: ToolContext, ToolRegistry, ToolSet, handlers. `ToolContext::env` is the turn's runtime environment, built in `core/agent.rs` (`turn_tool_context`) from config + thread by `core::context::runtime_tool_env`; `as_leaf` passes it on. Every child a tool starts (Bash foreground/background, `Skill_Exec`, `gh`, `git`, `invoke_subagent`/`read_thread` children via `ExecSubagentOptions::env`) gets it, and `$VAR` in tool paths reads it first. Never read per-run `ZDX_*` values from the process environment in tool code: concurrent turns share the process. Owns `BackgroundExecution`, the one per-run background policy (on, with an optional handoff bound; or off, where nothing is relocated and `Bash` has no implicit kill limit), resolved in `core/agent.rs` from `ToolConfig::background_commands`, the surface, and config. The handoff bound is only ever a relocation bound; the run deadline stays on `ToolContext::timeout`. The tool list, the `Bash` and `invoke_subagent` schemas, the handoff, and both `background: true` checks read it; do not add a second check keyed on subagent names or tool presence.
- `tools/orchestrator.rs`: the orchestrator's thread-control tools (unbound stubs in the default registry; the engine service rebinds them to its live `WorkerManager`)
- `tools/background.rs`: `run_background` (spawn+register a background process, invoked by the Bash tool on `background: true`) + `background_output`/`background_kill` agent tools (thread-scoped)
- `tools/gh_api.rs`: read-only GitHub REST tool over `gh api` (GET only, base64 content decoded, diff/raw media types); wraps `gh` because its token lives in the OS keyring
- `tools/git.rs`: read-only git inspection tool (`status`/`log`/`diff`/`show`); fixed subcommands and flags, operands rejected if they look like options
- `tools/list_models.rs`: read-only listing of the configured `[[model_modes]]` (name, description, primary, alternatives) plus the model registry with `zdx models list` semantics (enabled providers + custom-provider models as exact `provider:model` ids, display names, subscription flag, optional provider filter); gives shell-less agents — the orchestrator profile — verified ids to dispatch instead of guesses; model output capped at 200 entries with a narrowing note
- `tools/telegram.rs`: outbound Telegram tool (`send_message`/`send_document`/`create_topic`) over `telegram.rs`; shares its core with `zdx telegram`
- `tools/ask_media.rs`: one-shot media understanding tool (image/PDF/audio/video → text) over `media.rs`; read-only, shares its core with `zdx ask-media`
- `tools/memory_search.rs`: native memory search returning stable memory refs
- `tools/read_thread.rs`: read saved thread transcript tool
- `tools/subagent.rs`: invoke_subagent tool. Picks the mode from the run's policy: blocking (no background execution or no handoff bound), automatic handoff (normal call, `subagent_job::Launch::After(bound)`), or explicit background (`Launch::Immediate`). Every mode runs the child against a thread opened up front (`ChildThread::open`): a new tagged thread, or the `thread_id` being continued after `validate_resume_thread` (exists, `origin_kind: subagent`, same subagent name and root). Finished answers are `{result, child_thread_id}` (`subagent_job::child_answer`), so callers can continue the child (SPEC § Named subagents).
- `tools/subagent_job.rs`: managed subagents — `ChildThreadLock` (exclusive `flock` on the child thread file, released only when the child process exits: the managed child's exit callback keeps it, and a blocking call hands it to the child with `SupervisedChild::keep_until_exit` through `core::subagent::run_exec_subagent_holding`, so a dropped call cannot free it early; a second run of the thread gets `thread_busy`), `child_answer` (the shared finished-call result: answer shape, unused new-thread cleanup, id in failure details only while the thread exists), `run` (spawn via `core/subagent.rs`, adopt in `zdx_tools::adopted` and register with the turn at spawn, condense child events into the job log while relaying them live until the handoff, write the `subagent` registry marker only at the handoff; a child that exits first returns its blocking-call result and leaves nothing; `Lifecycle` + `ForegroundGuard` remove an abandoned call's logs and never-written child thread after the child exits), the `background_output` view, and `TurnTasks`/`TurnTasksGuard`, which stop a turn's background subagents when the turn ends. Owner lifetime is the turn; never rely on the caller collecting or on process exit. The turn's end is logged when the child reports it (`ChildEvent::TurnEnded`), never at stdout EOF: an answer must not depend on the process exiting. Every write to a job's event log goes through its `EventLog` (one lock, one whole line per record). A stop is attributed to the deadline only through `zdx_tools::adopted::claim_terminate`, which wins only when no other stop started first.
- `tools/skill.rs`: `Skill` (read-only: `SKILL.md` or one file inside the skill folder, through `read`) and `Skill_Exec` (`run`: a file under the skill's `scripts/`, every argument quoted, through `bash::execute_without_background`; `read`: pages output the run saved under `$ZDX_HOME/run/skill-exec/<thread>/`). Both reach only `ToolContext::skill_scope` (`skills::SkillScope`, set from `ToolConfig`), and every path is checked after canonicalization. Contract: SPEC §14, Skill tools.
- `tools/todo_write.rs`: structured todo/task tracking tool
- `tools/thread_search.rs`: thread discovery tool

## Conventions

- Keep `zdx-engine` UI-agnostic.
- No direct terminal UI logic here; the chat TUI is the Go program in `apps/tui`.
- Prefer `anyhow::Result` + `Context` at I/O boundaries.

### Test isolation and storage state

- Tests touching thread persistence/indexing or `$ZDX_HOME`-backed storage must hold `crate::test_support::temp_zdx_home()` for the duration of the test.
- Do not call `std::env::set_var`/`remove_var` directly in tests; use `temp_zdx_home()` or pure helpers.
- `temp_zdx_home()` returns an RAII guard (`TestZdxHomeGuard`) that acquires the engine test mutex, creates a `TempDir`, sets `ZDX_HOME`, resets `thread_index` caches, and restores original environment state on `Drop`.
- Do not introduce process-global `OnceLock<PathBuf>` or `LazyLock<PathBuf>` cached paths derived from `ZDX_HOME` or environment state.

### Logging / tracing

- Spans carry identity, events stay short. Existing spans: `turn` (`run_turn_inner`: `thread`/`model`/`provider`), `provider_request` (`request_stream`), `tool_turn` (`process_tool_turn`), `tool` (`ToolRegistry::execute_tool`: `tool`/`tool_use_id`). Log lines therefore read `turn:tool_turn:tool: … Tool failed`.
- Levels: lifecycle at `info`, per-request/per-tool detail at `debug`, failures at `warn`/`error`. Interruptions/cancellations are `debug`, not `warn`.
- Use structured fields with a stable literal message: `tracing::warn!(duration_ms, code, error = %msg, "Tool failed")`. Use `%` for display, `?` for debug.
- Logging an `anyhow::Error` requires `%format!("{err:#}")`, never a bare `%err`. anyhow's `Display` prints only the outermost `.context(…)` layer, so `%err` silently drops the cause that explains the failure; `?err` does walk the chain but emits a multi-line `Caused by:` block and breaks one-event-one-line.
- The alternate flag is anyhow-specific. For a concrete error type (`reqwest::Error`, `serde_json::Error`, `JoinError`) `{:#}` changes nothing, so pass `error = &err as &dyn std::error::Error` instead: `tracing` dispatches that to `record_error`, and the fmt layer appends the walked chain as `error.sources=[…]` on the same line. Use it for transport errors, where the cause (DNS, TLS) is the whole diagnostic value.
- MUST NOT log inside per-token / per-SSE-event / per-bash-chunk paths (`consume_stream`'s event loop, `handle_stream_event`, the `ToolOutputDelta` path). Log stream *ends*, not stream items.
- MUST NOT put prompts, full messages, tool inputs, error bodies, or secrets in fields; use `skip_all` on `#[instrument]` and truncate messages (`truncate_for_error`, `truncate_tool_error`).
- Tokio tasks do not inherit spans. When spawning (e.g. concurrent tool execution), attach the parent explicitly with `.instrument(tracing::Span::current())` or the context is lost.
- `tracing_init` pins noisy dependencies (`h2`, `hyper`, `reqwest`, `rustls`, `ignore`, …) to `warn` so `ZDX_LOG=debug` shows ZDX events instead of HTTP/2 frame dumps. Naming a crate in `ZDX_LOG` opts back in (`ZDX_LOG=debug,h2=debug`).

## Adding or updating models

- Canonical workflow: the project skill `.zdx/skills/model-provider-mgmt/SKILL.md`.
- Provider model lists live in the `default_*_provider()` functions in `src/config.rs`. `default_config.toml` is generated from them; never edit it directly.
- Run `cargo build` before `just update-defaults`, so the binary embeds the latest `config.rs`.
- `zdx models update` fills model data from models.dev, then the embedded `default_models.toml`, then OpenRouter, and last a zero-priced "(custom)" placeholder that needs a manual fix.
- Ask the user before applying a change to their own `~/.zdx/config.toml` or models registry.
